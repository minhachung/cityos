# CityOS architecture & design decisions

## Problem / user story

A city operations analyst wants to filter service requests by borough, type, status and date, inspect geographic distribution, and eventually compare resource allocation options. The MVP now does **exploration and illustrative review prioritization**, and deliberately does not claim dispatch capability.

## Data provenance

- Public data: [NYC 311 requests from 2020 to present](https://data.cityofnewyork.us/d/erm2-nwe9). The source updates daily, but this app imports on demand and may lag.
- Demo data: 18 fictional records generated at first launch. Source IDs carry a `DEMO-` prefix and UI labels them `DEMO`.
- API `source` flags ensure that mocked records can never silently masquerade as real public reports.

## Tech choices

- **React + TypeScript:** compositional UI with explicit data types for API results and filter state.
- **FastAPI:** typed request validation, autogenerated OpenAPI docs, async HTTP ingestion support.
- **SQLAlchemy / SQLite by default:** zero setup for local beginners; a PostgreSQL connection string is supported for deployment.
- **Leaflet:** open-source map visualization. Map popups escape external text before inserting into HTML.
- **Socrata 311 API:** includes query parameters to fetch only a bounded, recent set of columns/records.

## Data flow

1. At first launch, a few fictional demonstration records are created if the database is empty.
2. User chooses "Sync NYC 311 data"; the browser POSTs to `/api/ingest`.
3. Backend downloads a bounded set of official records, validates coordinates and timestamps and skips invalid rows.
4. Database stores each report with a unique `source_id`; repeated imports do not duplicate reports.
5. `GET /api/complaints` serves filtered, paginated records; `GET /api/stats` serves grouped counts.
6. `GET /api/priorities` fetches all matching unresolved stored requests (excluding demo records by default), scores each by documented category and report age, sorts before applying the output limit, and returns explainable score components.
7. React renders cards, map points, category chart, priority queue, and results table.

## Known limitations & safety

- Current counts do not represent NYC-wide totals. They describe the imported subset, including separately labeled fictional records.
- A non-closed status is treated as unresolved; a production system must establish official status semantics.
- A production environment requires access controls, input hardening, CORS configuration, monitoring, API quota handling, retries, and pagination beyond the latest 1,000 records per import.
- The importer does not update existing records' statuses. This is an intentional MVP simplification to improve later.
- Future prioritization should not infer emergency severity solely from number of complaints; real agencies would need operational rules and oversight.

## Planned phase 2: operational decisions

Build a *simulated* crew assignment system using synthetic crew records and actual 311 demand locations. Implement a transparent baseline (first-in-first-out) and a capacity- and travel-aware greedy heuristic. Once those are tested, evaluate Google OR-Tools and compare costs/travel under reproducible scenario seeds. Clearly distinguish simulation from production dispatch.

## Phase 2 prototype: transparent priority queue

File: `backend/app/priority.py`. Each unresolved record receives a deterministic score from a **student-defined** category rule (20–60 points) and days since reported (5/day, capped at 40). Future-dated reports receive 0 age points. The queue sorts by descending score, then earlier report date, then `source_id` to break ties reproducibly. Closed/resolved statuses are excluded and fictional demo data is excluded unless explicitly requested.

**Important assumptions:** This is not a validated operational policy, a prediction of harm, or an emergency-response tool. Categories are broad text-prefix matches and may not reflect actual impact. Age is measured at the date level to avoid assuming 311's timezone-naive timestamps are UTC. The imported status snapshot can be stale because the first importer only inserts new records. An authentic deployment would require operator-defined weights, validated labels, fairness checks, status refresh, and human approval.

**Scaling note:** The current endpoint reads all matching rows into memory to rank them before limiting results. That is acceptable for a bounded student demo but requires SQL-computed scores, indexing, and pagination for millions of records.


## v0.3: Fictional crew allocation simulation

`GET /api/allocation` collects the same database records as the priority queue, filters unresolved requests, omits demo data by default, and selects a bounded pool of top-scored, geocoded records. The `app/allocation.py` module matches records to **fictional** crews with predetermined category skills and one-job capacity. It uses straight-line Haversine distance, not roads or routing. An exact dynamic program over crew bitmasks maximizes priority minus distance. The FIFO comparison uses the exact same candidate pool, starting with the oldest request and choosing the nearest eligible remaining crew. Both summaries are displayed with assignment explanations in React. This is a reproducible demonstration of modeling choices, not evidence of municipal improvement.
